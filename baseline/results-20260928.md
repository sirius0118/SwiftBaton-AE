# RDMA baseline verification, 2026-09-28

The SwiftBaton-K release is sealed at tag `swiftbaton-k-ae-ct-batch-20260928`
(`dd2ff0d12bcaf5732d625458a6116b39e8afb850`). Its separate 500,000 ×
10 KiB, 32-client trial measured a 49.315 ms client-wide successful-operation
gap. The baseline trials below use 16 client threads and are not directly
matched to that release trial.

The matched baseline workload uses Node1 YCSB, Node2 source Redis, Node3
destination Redis, 500,000 indexed records of 10 KiB each, 16 client threads,
300 seconds of workload, a 20-second warmup, and a 30-second post-steady
sample. Both RDMA NICs had all priorities mapped to TC1 with a 25 Gbps
hardware rate limit. Each migration checked all 500,000 indexed key lengths
and a bytewise SHA-256 of an 8 MiB canary. Indexed values were not individually
checksummed.

The PCLive row used a separate CRIU build (SHA-256
`6edd309eba4c59c00c8c3ee9fc525c10431b862e75131193a9554e8ba8392167`)
on both hosts. Its actual selected binary hash is recorded in both
`result.json` and `state.json`. The post-copy and hybrid rows used the same
baseline CRIU binary (SHA-256
`1407bc8a858e924fa8a63a2fa8852129af9e86589159f94422c7e78c38cb26e0`)
on Node2 and Node3. The baseline runner checked that actual selected binary
before each run and restored both CRIU symlinks afterward. The older U driver
mistakenly wrote the sealed U build's hash to each run's `state.json`;
`result.json` contains the checked active-binary hash. The driver now records
`/usr/bin/criu` directly. The prior native-ibverbs post-copy and hybrid
trials remain archived at `sb_ae_20260928_070539` and
`sb_ae_20260928_071220`; their gaps were 261.295 and 301.379 ms, and their
TTR90 starts were 3.640 and 1.680 s. These individual runs do not isolate
the effect of changing transport.

The gap is the largest client-wide interval between successful DB returns
inside the migration window, using the intersection of all YCSB worker
intervals. TTR90 uses 100 ms throughput windows against the stable final
ten-second target throughput reference. Its start is the first window reaching
90% after service resumes; confirmation requires one second of sustained
recovery. Native CRIU can therefore have a short TTR90 **after** a very long
stop-and-copy gap.

The current implementations are functional algorithm prototypes. Native
CRIU streams images over userspace rsocket; PCLive, post-copy and hybrid-copy
send their image, PS and AS payloads over userspace rsocket; remote-fork uses kernel
RDMA. Kernel page faults cannot invoke the userspace rsocket API. These
observations are not transport-normalized speedups or independent paper
reimplementations. PCLive currently performs two snapshots: the second
re-reads all candidates locally but transfers only changed pages into the
same resident target memory. Source-side dirty-only reads and later rounds
remain to be implemented. The prior full second-round trial is archived as
`sb_ae_20260928_065735` (362.427 ms gap, 31.920 s TTR90 start); these are
single runs, not a statistical speedup estimate. The hybrid fragmentation
stress test used 1,048,576 logical
pages with 524,288 isolated pre-copy fragments and kept the file-descriptor
count at four. During the long demand-only remote-fork run, Node3 logged
hung-task warnings for inactive FT/BG dispatch threads. The run still passed,
reported zero transfer errors and released all module references after cleanup.

The native CRIU stream now uses up to eight concurrent rsocket lanes, with a
fresh connection for each 128 MiB image segment. In this full run the source
sent 6,401,695,558 bytes over 94 segment sessions in 5.614 seconds; the
target reported the same tree digest and zero relay transfer errors. The
earlier serial transfer (`sb_native_20260928_063745`) took 27.33 seconds
for a similarly sized image tree and its client gap was 212,507.265 ms.
The new gap was 183,958.048 ms. These are individual end-to-end runs; their
checkpoint and restore times also varied, so the gap difference is not a
controlled estimate of transfer-only benefit. The 8 MiB canary and all
500,000 indexed key lengths passed in the new run, and both CRIU selections
and owned containers were cleaned up.

The current PCLive rsocket full run (`sb_ae_20260928_102412`) read the initial
6,355,300,352-byte snapshot in 2.219 seconds over four persistent lanes. Its
second PS round transferred 73,617,408 metadata bytes and 942,702,592 changed
payload bytes in 0.431 seconds. Source and target agreed on 230,152 changed
pages, and the target refreshed exactly that many resident pages. All 500,000
indexed key lengths and the 8 MiB canary passed. The source and target also
agreed on image phases and all three AS lane write/receive/acknowledgement
counts. An earlier full run with rsocket PS and native-ibverbs AS
(`sb_ae_20260928_091321`) measured a 410.560 ms gap and 2.430 s TTR90 start.
These single-run end-to-end differences are not isolated transport effects.
The full rsocket PCLive trial initially exposed a late accepted TCP socket
missing from the PS socket catalog. The baseline now obtains the socket's
frozen FD endpoints and TCP state during IS before normal CRIU TCP repair.
The subsequent 100k regression and 500k trial passed. Two extra 100k runs
opened TCP connections across the PS-to-IS boundary and also passed, but the
source log did not show the late-FD fallback. Its rare branch remains unverified
under direct exercise.
